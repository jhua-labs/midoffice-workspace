## 1. 背景与问题（Why）

midoffice 订单系统目前只有「登录 / 未登录」两种状态：**任何通过认证的用户都能调用所有接口**——包括列出全部用户（`GET /users`）和删除订单（`DELETE /orders/{id}`）。

随着运营团队扩大，出现了真实风险：普通操作员误删订单、越权查看全量用户信息。业务方要求引入**基于角色的访问控制（RBAC）**，区分管理员与操作员的权限边界。

同时，运营团队目前只能靠 curl / Postman 调 API，没有可视化操作界面。业务方要求配套一个**轻量前端管理界面**，让操作员/管理员在浏览器里完成日常订单操作，并让 RBAC 在 UI 上直观可见（管理员才看得到删除按钮、用户管理入口）。

## 2. 目标（Goals）

- 为用户引入**角色**概念，按角色限制敏感操作（后端 RBAC）。
- 交付一个**前端管理界面**，覆盖登录、订单列表/详情/创建/改状态/删除、用户列表，并按角色门控敏感操作。
- 不影响现有登录流程和已上线的订单操作；**不修改后端源码即可接入前端**。
- 权限规则后续可配置（本期先固化两种角色，预留扩展）。

## 3. 范围（Scope）

### In Scope
- **增量一（后端 RBAC）**：两种角色 **ADMIN（管理员）**、**OPERATOR（操作员）**；在认证基础上增加授权校验；受控接口权限矩阵（见第 5 节）。
- **增量二（前端界面）**：独立的单页应用（SPA），调用既有 REST API；实现登录、订单管理、用户列表；把 RBAC 落到 UI（角色门控按钮/视图）。

### Out of Scope（非目标）
- 不做细粒度的资源级/字段级权限。
- 不做角色的自助申请/审批流程。
- 不引入外部 IAM / SSO。
- 不支持运行时动态修改用户角色（改角色需重新登录获取新 token）。
- 前端不做复杂的状态管理/离线能力/国际化；只覆盖上述核心操作。
- **不修改后端源码**：前端作为独立模块接入，经开发代理调用 API（部署形态另议）。

## 4. 角色定义

| 角色 | 说明 |
|------|------|
| ADMIN | 管理员，拥有全部权限，含用户管理与订单删除 |
| OPERATOR | 操作员，可处理订单日常操作，但不能查看全量用户、不能删除订单 |

## 5. 功能需求（What）

### 5.1 后端 RBAC

| 编号 | 接口 | ADMIN | OPERATOR | 说明 |
|------|------|:-----:|:--------:|------|
| FR-1 | `GET /orders` | ✅ | ✅ | 列订单，两者都可 |
| FR-2 | `GET /orders/{id}` | ✅ | ✅ | 查订单详情，两者都可 |
| FR-3 | `POST /orders` | ✅ | ✅ | 创建订单，两者都可 |
| FR-4 | `PUT /orders/{id}/status` | ✅ | ✅ | 改订单状态，两者都可 |
| FR-5 | `DELETE /orders/{id}` | ✅ | ❌ | **仅 ADMIN** 可删除订单 |
| FR-6 | `GET /users` | ✅ | ❌ | **仅 ADMIN** 可列出全部用户 |
| FR-7 | `GET /users/me` | ✅ | ✅ | 查看自己，两者都可 |

- FR-8：登录成功后，用户的角色信息需可在授权时被系统识别（具体存储/传递机制为架构决策，见第 8 节）。
- FR-9：无权限的请求返回 **403 Forbidden**，响应体为 `{"error":"Forbidden"}`（与现有 `Map.of("error", ...)` 错误格式一致；区别于未认证的 401）。

### 5.2 前端管理界面

| 编号 | 需求 | 说明 |
|------|------|------|
| FR-10 | 登录页 | 用户名/密码登录，成功后保存 JWT，后续请求带 `Authorization: Bearer` |
| FR-11 | 订单列表 | 展示所有订单（PNR/乘客/金额/状态）；ADMIN 与 OPERATOR 都可见 |
| FR-12 | 订单创建 | 表单创建订单；两角色都可 |
| FR-13 | 订单改状态 | 修改订单状态；两角色都可 |
| FR-14 | 订单删除按钮 | **仅 ADMIN 可见/可用**；OPERATOR 界面上不渲染该按钮（角色门控） |
| FR-15 | 用户管理入口 | **仅 ADMIN 可见**；OPERATOR 导航中不出现该入口 |
| FR-16 | 角色感知 | 前端从 JWT 解出角色，据此条件渲染；未登录跳登录页 |

## 6. 验收标准（Acceptance Criteria）

### 后端
- AC-1：OPERATOR 调用 `DELETE /orders/{id}` 返回 **403**，订单未被删除。
- AC-2：OPERATOR 调用 `GET /users` 返回 **403**。
- AC-3：ADMIN 调用上述两个接口正常成功（200/204）。
- AC-4：ADMIN 与 OPERATOR 调用 `GET/POST /orders`、`GET /users/me` 均正常。
- AC-5：未携带有效 token 的请求仍返回 **401**（现有行为不变）。
- AC-6：现有 5 个集成测试全部继续通过（不得回归）。
- AC-7：种子用户初始角色固定为 alice = ADMIN、bob = OPERATOR。
- AC-8：不含 role claim 的旧 token 一律按最小权限视为 OPERATOR，不得当作 ADMIN。
- AC-9：403 响应体为 `{"error":"Forbidden"}`，格式与现有错误响应一致。

### 前端
- AC-10：以 alice（ADMIN）登录后，订单行显示**删除按钮**、导航含**用户管理**入口。
- AC-11：以 bob（OPERATOR）登录后，**看不到删除按钮**、**看不到用户管理**入口。
- AC-12：教学关键点——即使隐藏了删除按钮，OPERATOR 直接调用 `DELETE /orders/{id}` API 仍必须被后端拦截返回 **403**（UI 门控 ≠ 安全，后端 RBAC 才是真正防线）。
- AC-13：前端接入过程**未修改任何后端源码**（后端文件字节级不变）。

## 7. 约束（来自现有系统，需架构阶段遵守）

- 不得破坏现有 `POST /auth/login` 的请求/响应契约。
- JWT claim 结构只可**新增**（如加 role），不得改动或删除现有 claim。
- 不得删除/重命名现有文件与现有公开接口。
- 现有内存存储与种子数据机制沿用，不引入外部数据库。
- 前端为**独立模块**（`frontend/`），不得改动 `src/` 下后端源码；开发期经代理调用 API 以规避 CORS。

## 8. 架构阶段待决（Deferred to Architecture）

- **角色的存储/传递机制**（写入 JWT claim vs 每次从用户存储查）为架构阶段决策。PRD 层面只要求"授权时可获取角色"（见 FR-8）。现有约束"JWT claim 只可新增"使 **claim 方案成为自然候选**；最终由架构定，并记录 trade-off（若写入 claim，则改角色需重新登录——本期已在 Out of Scope 声明不支持运行时改角色）。
- **前端技术栈与接入形态**（SPA 框架、开发代理 vs 后端配 CORS、构建/部署方式）为架构阶段决策。PRD 层面只要求"独立模块、不改后端、角色门控可见"（见 FR-10~16、AC-13）。
